# 04 — Design principles

Derived from docs 01–03. Each pillar states the rule, the rationale, and
what it *costs* — a principle that forbids nothing is not a principle.
These are commitments for v0.1 design work; changing one requires an ADR
that names which pillar is being traded away and why.

## Pillars

### P1. Sound core, no escape hatch in the type system
No `any`, no unchecked casts in normal code. The unsafe/dynamic boundary
exists only at FFI and serialization edges, and is loud and auditable.
*Rationale:* TS's unsoundness is its permanent tax (doc 01); machine-written
code makes advisory types worthless. *Cost:* some dynamic idioms are simply
unwritable; migration of untyped data requires explicit decoding.

### P2. Types have a budget: structural + unions + generics, no type-level programming
Structural records, discriminated unions with exhaustive matching,
flow-sensitive narrowing, parametric generics with simple bounds. No
conditional/mapped/dependent types, no macros in v1.
*Rationale:* TS shows where expressivity curdles into golf; Go shows
austerity backfires. The budget line is drawn *above* sum types and
*below* type-level computation. *Cost:* some libraries (ORMs, fancy
builders) can't offer TS-grade type magic. Accepted.

### P3. Annotate public boundaries; infer everything inside
Exported functions/types require full signatures; function bodies and
module-private code are inferred. Module-local inference only — never
whole-program (Crystal's grave, doc 02).
*Rationale:* readability without noise; stable documented APIs; anchors
that make LLM-generated diffs reviewable; compile-speed locality.
*Cost:* a little ceremony exactly where ceremony pays.

### P4. Processes, not threads; supervision in the runtime, not a library
Isolated lightweight processes with message passing as *the* concurrency
model — no shared-mutable-memory concurrency in the language at all.
Supervision trees, restart strategies, and typed process references are
runtime/stdlib primitives.
*Rationale:* doc 01 §4; races impossible by construction beats races found
by tooling. *Cost:* building a real runtime (scheduler, per-process heaps,
preemption or safepoint-preemption); some raw-throughput patterns
(shared-memory parallelism) need runtime-provided primitives instead.

### P5. Errors are values; propagation is one character
Result/Option types with `?`-style propagation sugar and exhaustiveness
checking; panics only for bugs, and a panic kills only its process —
supervision turns crashes into restarts, not outages.
*Rationale:* merges Go's honesty, Rust's ergonomics, and Elixir's
"let it crash" into one coherent story. *Cost:* no exceptions; API authors
must think in results.

### P6. One toolchain binary, zero configuration
`lang build|test|fmt|check|doc|pkg` in a single binary. The formatter has
no options. No build scripts in v1; no compiler flags that change language
semantics — one language, one meaning.
*Rationale:* Go's highest-leverage lessons (doc 01 §2); dialect-free code
is what keeps large codebases and model-generated code uniform.
*Cost:* power users will chafe. Let them.

### P7. Compile speed is a budgeted feature
Hard budgets from day one, enforced in CI on a growing benchmark codebase:
incremental check < 1s at 100k LOC; clean build < 60s at 100k LOC on a
laptop. Language features that break the budget get redesigned — the
budget doesn't move.
*Rationale:* the edit-loop is why dynamic languages *feel* productive; Go
proves a static language can keep it. Crystal proves what happens
otherwise. *Cost:* constrains inference scope and metaprogramming forever.

### P8. Single static binary out; boring ops
`lang build` emits one native binary with the runtime inside. Cross-
compilation built in. No VM install, no dependency dir at runtime.
*Rationale:* Go's adoption engine; the anti-BEAM-ops, anti-node_modules
story is half our pitch. *Cost:* rules out targeting BEAM/JVM as the
*primary* backend (either may still be a secondary target, RQ4).

### P9. Readability is a review gate, not an aspiration
Python-class surface: low sigil count, keyword-forward, indentation-
friendly, no semicolon/brace ceremony debates (the formatter ends them).
Every language feature is evaluated by writing the 10 canonical sample
programs (doc 05, RQ3) *before* implementation — samples first, grammar
second, implementation third.
*Rationale:* code is read (by humans reviewing machines, increasingly) far
more than written. *Cost:* slower feature intake; some expressive syntax
rejected for being clever.

### P10. Runtime-checkable types at the edges
Types don't erase at process and serialization boundaries: decoding
`JSON → T` and message-passing across version boundaries are checked by
the same type definitions, generated by the compiler — no parallel schema
language (no zod-equivalent needed).
*Rationale:* TS erasure forced the ecosystem to invent types twice
(doc 01 §1). *Cost:* runtime type descriptors in the binary; design care
at hot-reload/rolling-deploy edges.

### P11. Fat standard library, stable promise
Batteries for services: HTTP, JSON, crypto-basics, time, testing,
logging/metrics/tracing hooks, process/supervision toolkit. Post-1.0, a
Go-style compatibility promise.
*Rationale:* ecosystem cold-start mitigation #1 (docs 02–03); uniformity
across codebases. *Cost:* stdlib maintenance burden; slower stdlib churn.

## Non-goals (v1)

- No macros or compile-time metaprogramming.
- No shared-memory concurrency, no bare threads in the language.
- No exceptions.
- No inheritance; composition + structural interfaces only.
- No REPL-first workflow promises (fast check loop instead; revisit later).
- No GPU/numerics story, no embedded/no-runtime mode, no browser target.
- No configuration knobs that fork the language into dialects.

## Open tensions to resolve by ADR (not silently)

- Preemptive scheduling vs safepoint cooperative scheduling (RQ2).
- Full per-process heaps vs shared-immutable + per-process nurseries (RQ2).
- Mutability model inside a process: fully immutable (Elixir-style) vs
  locally mutable/`let mut` (Swift/Rust-style ergonomics) — affects P4,
  P9, and GC design. Sample programs will decide.
- The strategic interop bet: C-ABI only vs BEAM secondary target vs WASM
  components vs Roc-style embedding platforms (RQ4).
